# Compatibility model and rule reference

This page lists Epoch's built-in findings: 93 compatibility rule IDs, 15 measured operational rule IDs, and five static lint hints. Runtime failures and checkpoint states are listed separately. A rule's evidence and supported scope determine its verdict; a successful SQL parse or an empty catalog diff alone is not a compatibility proof.

Use [verification boundaries](verification.md) for the workflow and examples, [contract metadata](contracts.md) for the evidence format, and [CI policy](ci.md#compatibility-ci-policy) for exit codes. Each table below describes an emitted rule and the limits of its proof; multiple rules can apply to the same change.

## Scope and aggregation

- `SAFE` is a positive result within the explicitly supported structural or mapped data-domain model. It is not whole-application behavioral equivalence, exhaustive SQL discovery, or operational safety. A single SAFE finding describes one fact; other findings can make the report UNKNOWN or BREAKING.
- Compatibility aggregation is BREAKING over UNKNOWN over SAFE. An unsupported/incomplete model remains UNKNOWN even if all SQL prepares. An empty unestablished contract cannot prove safety.
- Every pending schema state is compared to the **original application's baseline**, not merely the immediately previous migration. Earlier intermediate failures remain in the report if a later migration restores the schema. The immediately preceding snapshot is also used to select statements for replanning.
- Baseline health is evaluated separately, with `migration=null`. The final report removes repeated baseline issues from pending-migration findings. Baseline-invalid operations cannot be used as positive structural regression witnesses. Rejected generated queries also invalidate their linked mapping provenance.
- Accepted-baseline files require an exact baseline fingerprint and per-finding justification. They affect `gateVerdict`, never turn an UNKNOWN finding into a proof, and cannot suppress pending or data-direction regressions.
- New-on-old schema verification checks the new contract against the retained original schema. It is not execution or proof of down migrations. New-writes-old-reads is a separate final-schema assessment; it does not claim new writers ran against each intermediate deployment state.
- PostgreSQL supplies actual catalog objects, SQL preparation, parameter inference and result descriptions. Supported CHECK fragments are parsed from catalog expressions. Migration parsing only identifies effects outside the catalog model; it is not the source of schema truth.
- PostgreSQL identifiers are normalized to its 63-byte representation. Dotted quoted schema/table components cannot currently be represented unambiguously by the flattened `schema.table` format.
- Whole-row data admission is a deliberately small **schema/input-domain witness**, not an executed Hibernate INSERT or a proof about current unique-key occupancy, application validators or external behavior. Native/runtime queries do not acquire generated mapped provenance merely by referring to the same table.
- `--fail-on breaking|unknown` changes exit policy only, not JSON verdicts or findings. The default `unknown` blocks UNKNOWN; `breaking` permits it. Runtime/incomplete remains exit 3. Operational assessment and its opt-in gate remain independent.
- `catalogChanged=false` describes the immediate before/after inspected catalog. It filters redundant SAFE detail for that unchanged step, not UNKNOWN/BREAKING evidence or arbitrary DML/procedural effects. Structural comparisons still use the original baseline. Separate optional `findingChanges` follows continuing rule/object/verdict/caller episodes; no longer reported is not an independent SAFE proof.
- Optional `findingGroups` presents established shared sources for `DATABASE_BEHAVIOR_DEPENDENCY_UNPROVEN`, `EXISTING_DATABASE_BEHAVIOR`, and `RELATION_RENAME_EXPRESSION_UNPROVEN`. It preserves every raw finding, current migration attribution and acceptance fingerprint. Grouping does not equate local expression semantics or prove compatibility; [reporting limits](reporting.md) describe the exact scope and denominators.
- Grouping preserves every source: `UNRESOLVED_QUERY` uses an unresolved diagnostic's `affectedIds` (or its legacy `id`) and does not duplicate an already represented access-path failure. Terminal source samples are capped, but JSON retains the full inventory. Group counts and distinct source counts have different denominators.

## Shared proof boundaries

**Structural write proofs.** New NULL/type/enum rejection requires a valid old mapping, direct supported writable domain, relevant baseline acceptance, and ordinary relation/type facts. Raw `hibernateNullable` is not a Kotlin/Java declaration; missing `declaredNonNull` is unknown. Hibernate custom SQL/JavaType/JdbcType/converters, custom write expressions, dynamic mutation variants and a disabled null-check setting conflicting with raw mapping nullability prevent complete producer facts. An entity ID covering both INSERT and UPDATE cannot make an UPDATE fact prove an omitted INSERT value. Type defaults, identity, generated columns, triggers/rules/RLS/inheritance and existing-row validation status are considered where relevant.

**Supported literal/default/type fragments.** Constant defaults are the small builtin scalar/literal grammar in `RuleProofs.constantDefault`, not arbitrary immutable functions. Known sequence defaults are exact builtin `nextval` over a catalog-resolved sequence with a supported search path. String widening is bounded varchar to a larger bound or unbounded text/varchar; integer/numeric widening must also respect read representation. Integer narrowing intersects physical, JDBC and declared Java ranges. String narrowing may use a declared bound, an explicit unbounded declaration, or positive `stringInputLengthUnrestricted` evidence for the standard direct String binder. The last fact overrides a shorter raw DDL hint; missing length alone remains unknown. Decimal narrowing needs supported precision/scale. Finite relational enum labels take precedence over generic column length.

**CHECK fragments.** Only complete scalar `column IS NOT NULL`, finite string equality/IN/ANY array catalog forms and their supported casts are used by these compatibility rules. Composite-row `IS NOT NULL` differs from scalar NOT NULL. Enum comparison requires supported text/varchar semantics, default collation and established builtin resolution; CHAR padding, custom operators/casts, arbitrary checks and nondeterministic collations are not assumed equivalent. NOT VALID checks can reject unrelated-column UPDATEs of existing rows; validated-existing-row coverage or complete replacement provenance is required for SAFE.

**Index bounds.** Physical builtin Btree key plus INCLUDE-column size is checked on supported 8 KiB PostgreSQL pages, with a conservative 2,000-byte tuple ceiling and overflow-safe length arithmetic. Unbounded TEXT/VARCHAR can instead use actual relational enum values from exact baseline-valid generated writer/mapping links, complete direct input domains, known operation-local effects and supported builtin storage. Every actual INSERT and UPDATE is proved separately. Omitted/DEFAULT values have independent NULL/constant proofs; a native writer cannot borrow another mapping's enum set. Unchanged UPDATEs can preserve existing valid/ready tuples only if every key/INCLUDE column is untouched and none is generated. Partial key updates cannot borrow mapping bounds for retained unbounded historical values. UTF-8 bytes, repeated index columns and full tuple size count. Raw `@Column(length)` on TEXT, converters, malformed strings, opaque defaults, unknown writers, expressions, partial/custom indexes and unsupported methods do not become finite proofs.

**Read widening.** `ReadCompatibility` requires unique baseline-valid direct Hibernate reader provenance, complete actual selected-column coverage, `readDomainComplete`, and `mappedReads.resultPosition` for each changed actual JDBC slot. Standard String reads preserve supported text-family values. Integer decoders either cover the entire target type or require a recognized value-preserving migration history plus a closed declared producer set preserving the decoder range. Each producer and omitted INSERT/default is checked; arbitrary native writers, custom conversion, generated values and reached opaque effects block that invariant. Native/exact result declarations stay strict. A predicate-only dependency or guessed label is not a decoded field. These proofs concern the declared old operations, not external writers or arbitrary mixed-version production data.

**Scoped database behavior.** Complete version-1 catalog roots from `pg_depend`/`pg_rewrite` and relation/operation attachments drive semantic rules, changed-object intersection, query revalidation and cache eligibility together. INSERT defaults, actual DEFAULT assignments, generated columns, type semantics, triggers, policies, views, rules and incoming FK actions activate according to the operation. A materialized-view read does not execute its defining query. A view referencing a table is not a callback on every direct table operation. Reached opaque functions retain hidden-name/unknown-side-effect uncertainty only on their callers. Graph dependency completeness does not prove arbitrary semantic equivalence. Ordinary row triggers affect runtime proofs without necessarily being evaluated by planning; reached possibly planning-evaluated code prevents unsafe reuse/parallel/cache use. Missing nodes, incomplete/unsupported graph versions and legacy nonempty inventories retain conservative limits. Extension changes remain globally conservative because overload resolution and extension scripts are not proven equivalent merely by known caller links.

Known original system objects form the graph's implementation boundary: pinned dependencies and original OIDs below 16384 are recognized only for supported catalog kinds. A user object does not become builtin by living in `pg_catalog`. Explicit system-catalog reads can observe application DDL and retain caller-local uncertainty. Unchanged clock defaults (`CURRENT_TIMESTAMP`/`now()`) and bounded builtin scalar CHECK/index expressions can have closed dependencies without being constant values or proving a changed constraint/index safe. Actual function, operator, type and index-method dependencies remain independent guards.

Each uncertain root uses its own dependency closure, rather than every object reached by a joined caller. Fully walked nonrecursive read-only CTE/EXISTS/derived-query forms with complete physical inventories may bound syntax uncertainty to their dependencies; they still retain baseline semantic debt and conservative planning eligibility. Unknown inventories, hidden lookups, custom casts/operators and recursive or writable forms do not acquire that boundary. Proven compatibility-view renames can normalize exact unchanged owned default/generated/CHECK/index attachments. This suppresses identity churn only; changed expressions, function bodies and hidden name observers still need proof.

**Mapped data direction.** Actual selected decoder bindings (`mappedReads`) and exact generated writer links (`mappedEntityIds`) are required. The positive reader subset is the standard single-table, single-id loader with actual immediate BasicFetch/value-index/physical-column links, without extra predicates/restrictions/unsupported hydration paths. Candidate admission currently establishes supported direct INSERT rows only; UPDATE-only candidate production remains unproven. Final NOT NULL, supported CHECKs, physical types, supplied/omitted values and supported index tuple bounds matter. FK/exclusion/general checks, generated/identity fields and opaque relation effects block an unsupported whole-row witness. Supported intrinsic finite enum encodings are NAME, ORDINAL and explicit codes; the actual aligned relational values matter. JDBC numeric lexical normalization and Java `String.trim()` in old NAME decoding must not create false raw-string differences. Unknown explicit codes may decode to null rather than throw. Converter bytecode equality is not a semantic equivalence proof.

| `GENERATION_CHANGED` | UNKNOWN | An identity/generated expression on a relation with declared dependencies changes without supported stronger proof. | A generator's presence is not arbitrary generator equivalence. |

## PostgreSQL planning, execution witnesses and migration effects

Sources: `postgres/PostgresQueryPlanner.kt`, `PostgresBoundaryProbes.kt`, `MigrationClassifier.kt`, `PostgresVerifier.kt`.

| Exact rule ID | Possible verdict | Evidence / proof basis | Conservative boundary / next action |
| --- | --- | --- | --- |
| `BASELINE_SQL_UNVERIFIED` | UNKNOWN | Original template cannot be accepted by supported PREPARE/EXPLAIN/Describe, parameter inference or declared result comparison. | Baseline health, not a migration failure; ambiguous unknown/text parameter inference needs explicit type/context. |
| `POSTGRES_SQL_REJECTED` | BREAKING or UNKNOWN | Baseline-accepted SQL with frozen baseline parameter types is rejected after migration. BREAKING for SQLSTATE class 42, schema error 3F000 or synthetic result mismatch; UNKNOWN for other non-infrastructure failures. | Infrastructure SQLSTATEs/exceptions escape as failed verification, exit 3. Passing PREPARE is not full behavior proof. |
| `RESULT_SIGNATURE_CHANGED` | BREAKING or UNKNOWN | PostgreSQL result labels/types differ from the accepted original result and the actual mapped decoder/position proof does not establish compatibility. BREAKING for exactResultShape or explicit resultColumns; otherwise UNKNOWN. | Labels/count stay exact. Standard supported reads may avoid this finding after value-preserving widening; native/missing/ambiguous/custom bindings do not inherit that proof. JDBC serial decoration is normalized using actual storage/generation facts. |
| `BOUNDARY_EXECUTION_REJECTED` | BREAKING | Optional rollback probe actually accepted supported old INSERT rows at baseline and now rejects the same typed witness with SQLSTATE class 22/23 or 54000. | Samples never emit SAFE. Only bounded direct INSERTs and safe execution contexts are probed; unsafe generation/custom behavior/unsupported types are skipped. Runtime failure is exit 3. |
| `UNSUPPORTED_MIGRATION_EFFECT` | UNKNOWN | Actual migration statement has data/procedural/unsupported effects outside the catalog-only model, or cannot be classified. | PostgreSQL executes it in isolation; regex/AST classification cannot establish arbitrary DML or procedural equivalence. Literal SET/SET LOCAL lock_timeout changes only acquisition policy; other settings, set_config calls, DROP+CREATE same name and unproved USING transformations remain unsupported. |
| `MIGRATION_EFFECTS_UNAVAILABLE` | UNKNOWN | Exact migration resource could not be read for effect classification after execution. | Schema/planning evidence can still report concrete failures, but uninspected effects cannot be silently SAFE. |
| `FLYWAY_CALLBACK_UNSUPPORTED` | UNKNOWN | Baseline/pending SQL lifecycle callback file discovered; callbacks are outside the supported contract and were not executed. | Use versioned migrations for required changes or verify callback behavior separately. |
| `MIGRATION_DATABASE_CALLBACK_UNPROVEN` | UNKNOWN | Measured statements encounter applicable event callbacks/opaque database effects that can mutate data beyond catalog observations. | Aggregates matching causes and statement ordinals from operational callback evidence. This is compatibility uncertainty as well as an independent operational assessment; unchanged catalogs do not prove unchanged data. Exact affected application paths are not invented. |

A fresh committed verification session that differs from the known baseline policy produces UNKNOWN `POSTGRES_SQL_REJECTED` evidence with the synthetic marker `EPOCH_SESSION_UNPROVEN`; PostgreSQL did not reject the query, and no SQL/boundary execution is credited under that unsupported policy. Session changes invalidate reuse independently of catalog changes, including recovery to the baseline policy. This adds no new compatibility rule ID.

Planner detail worth spelling out: PREPARE derives OTHER/native parameter types from the actual baseline PostgreSQL expression/catalog context; inferred types are frozen for later states. EXPLAIN is without ANALYZE, and Describe does not execute the DML. This still does not assert arbitrary planning-time functions have no side effects; existing planning/execution safety guards and behavior limitations remain part of scope.

| `DATA_READ_EFFECT_UNPROVEN` | UNKNOWN | Old view/inherited relation may expose values written through another physical relation. | Different relation names alone do not establish disjoint data effects. |
| `DATA_WRITE_EFFECT_UNPROVEN` | UNKNOWN | New statement lacks supported complete direct effects, or triggers/rules/RLS/inheritance/generated/default/CHECK/index/FK actions can change stored values indirectly. | Includes native/unaccepted/incomplete statements and unproven SELECT effects; a known unrelated target cannot establish disjointness from incomplete dependencies. |
| `DATA_READ_PROVENANCE_UNPROVEN` | UNKNOWN | Old actual selected decoder set, accepted final plan or physical mapped binding is missing/incomplete. | Predicate-only SQL dependencies are not decoded fields; legacy mapping-only contracts cannot invent reader evidence. |
| `DATA_WRITE_PROVENANCE_UNPROVEN` | UNKNOWN | Actual INSERT/UPDATE lacks exact generated mapping/target/column domain, or subtype INSERT lacks captured literal discriminator. | Native/manual metadata cannot borrow an unrelated entity's finite domain. |
| `DATA_IMPLICIT_WRITE_UNPROVEN` | UNKNOWN | New INSERT omits an old decoded column without supported implicit value-domain proof. | A narrow unchanged generated-ID omission is separately recognized; arbitrary defaults/identity values are not inferred. |
| `DATA_CONVERTER_SEMANTICS_UNPROVEN` | UNKNOWN | Unsupported converter semantics, changed/opaque converter, or an unfamiliar explicit enum code whose old converter may return NULL. | Equal bytecode hashes do not prove helper/configuration equivalence; do not assume every unknown code throws. |
| `DATA_TYPE_MAPPING_UNPROVEN` | UNKNOWN | Producer/decoder codec/domain is incomplete or changed, or physical/JDBC extraction can transform the compared representation. | Numeric text `01`, padded NAME inputs, CHAR/custom casts and unsupported logical changes require more proof, not raw set-difference BREAKING. |
| `DATA_WRITE_ACCEPTANCE_UNPROVEN` | UNKNOWN | Candidate lies outside old read domain but complete final-schema row admission is unavailable. | UPDATE-only witnesses, FK/exclusion/unsupported CHECK/default/generation/index/opaque effects remain conservative. |
| `DATA_NULL_DOMAIN_UNPROVEN` | UNKNOWN | New NULL exclusion or old NULL acceptance lacks sufficient declared/mapped/physical facts. | Missing declarations are not inferred from annotations or absence of observed NULLs. |
| `DATA_POLYMORPHIC_READ_UNPROVEN` | UNKNOWN | Physical finite hierarchy, concrete producer or old unrestricted root encounter is incomplete. | JOINED/UNION/formula/synthetic/wildcard/forced-filter cases do not become single-table positive proof; missing discriminator cannot fall through to SAFE. |
| `DATA_ENUM_VALUE_UNREADABLE` | BREAKING | A supported new enum relational value is admitted by final row-domain proof but outside the old standard finite decoder. | Actual encoding/representation and exact old selected decoder are required; final CHECK/type exclusion cancels this candidate. |
| `DATA_ENUM_VALUE_REINTERPRETED` | BREAKING | Same admitted stored enum value maps to different named logical constants across releases. | Actual aligned relational codes, not Java declaration order alone; stable explicit codes and native NAME storage avoid false ordinal reorder reports. |
| `DATA_NULLABILITY_RELAXED` | BREAKING | Actual supported new nullable writer can store admitted NULL into a column decoded under an old declared non-null domain. | Reports a declared read-domain violation, not a universal claim that Kotlin field hydration necessarily throws. |
| `DATA_DISCRIMINATOR_UNREADABLE` | BREAKING | Actual concrete single-table INSERT supplies admitted literal discriminator unknown to an old complete unrestricted root decoder. | Physical/JDBC normalization, conditional root readers, abstract/read-only producers and schema-excluded literals cannot fabricate breakage. |
| `DATA_DOMAIN_PRESERVED` | SAFE | Supported equal/narrower decoded value domains remain included; incompatible candidates are excluded by final schema; known discriminators remain accepted; or complete ordinary operation dependencies are disjoint. | Positive code/domain/provenance facts required. Any unsupported relevant path still contributes UNKNOWN; this is final-schema mapped-domain scope only. |

## Measured operational findings: separate verdict domain

Source: `core/OperationalAssessmentRules.kt`, fed by `postgres/PostgresOperationalMonitor.kt` and `OperationalSql.kt`. These are not the 93 compatibility rules. `OperationalVerdict` aggregates RISKY over UNKNOWN over SAFE; lock exposure, scans and rewrites may be operationally risky while structurally compatible. Same-connection lock/timeout observations, physical identity and catalog-corroborated command meaning supply the evidence. A regex/AST classification alone is not a measured proof. All SAFE actions require complete modeled effects and no applicable opaque callback. Independent RISKY evidence remains even when a separate metadata action is SAFE.

| Exact rule ID | Possible verdict | Evidence / proof basis | Conservative boundary / next action |
| --- | --- | --- | --- |
| `OP_WRITE_BLOCKING_LOCK` | RISKY | An old table has an observed write-conflicting lock, or a separately labeled lock mode required by a catalog-confirmed supported command, without established migration-authored acquisition protection. One finding retains its modes, baseline identity and timeout evidence. | Measured evidence applies even to unsupported SQL. Required-mode evidence covers bounded commands after autocommit releases locks; it never fabricates sampled locks. A positive authored before-timeout exempts only supported ordinary commands with unchanged settings and complete effects. It neither proves short lock duration nor waives blocking scans/rewrites. |
| `OP_TABLE_REWRITE` | RISKY | The same preexisting physical table/materialized-view identity has different nonzero storage identity after the statement. | Unknown old/new identity stays UNKNOWN; new-window storage has a separately guarded exemption. Plan expand/backfill/contract or explicit production locking/capacity. |
| `OP_INDEX_BUILD_BLOCKS_WRITES` | RISKY | Catalog-confirmed nonconcurrent index build on an old relation invokes PostgreSQL's ordinary scan under ShareLock. | Empty after-autocommit samples do not prove no lock was held. Prefer a supported concurrent build outside a transaction. |
| `OP_NOT_NULL_SCAN` | RISKY | SET NOT NULL on an old nullable column without a prior supported validated non-null CHECK requires validation under AccessExclusiveLock. | Unknown prior facts stay UNKNOWN. Stage NOT VALID CHECK, commit, validate, then use the positive invariant. |
| `OP_CONSTRAINT_VALIDATION_BLOCKS_WRITES` | RISKY | Immediate validated CHECK/FK installation inspects preexisting owning/referenced relations under blocking lock semantics. | Account for referenced relations and physical identity, not just the named new child table. Split installation and validation with appropriate committed boundaries. |
| `OP_VALIDATION_UNDER_RETAINED_LOCK` | RISKY | A recognized scan runs while a preexisting table is already held under a write-blocking lock, including locks from prior statements in that transaction. | An after-only lock observation is not automatically evidence it existed during the scan. Release strong locks before validation/build. |
| `OP_VALIDATION_UNDER_COMPOUND_LOCK` | RISKY | A scan shares one ALTER TABLE with a catalog-confirmed stronger subcommand on the same old physical relation; PostgreSQL acquires the maximum lock first. | A post-statement unexplained compound lock retains UNKNOWN rather than guessing timing. Separate strong metadata change and scan into committed phases. |
| `OP_ONLINE_INDEX_BUILD` | SAFE | Supported successful concurrent index build has catalog-confirmed valid/ready index, observed autocommit and no retained old-table blocking scan lock. | Does not prove fast completion or no long-transaction/I/O waits. Conflicting transaction facts, custom expressions/opclasses or opaque callbacks do not become SAFE. |
| `OP_DEFERRED_CONSTRAINT_VALIDATION` | SAFE | Catalog-confirmed CHECK/FK NOT VALID installation skips its initial existing-row validation scan. | Lock acquisition/later validation and structural writer compatibility remain separate. New constraints can reject old writes despite operational SAFE. |
| `OP_NONBLOCKING_VALIDATION` | SAFE | A previously unvalidated supported constraint becomes validated under ordinary validation semantics with complete identities and no retained/compound old-table blocking lock. | Unknown relation identity or callback/scan effects block proof. This does not estimate production duration. |
| `OP_VALIDATED_NOT_NULL` | SAFE | Prior physical NOT NULL or a supported validated scalar non-null CHECK establishes scan-free SET NOT NULL. | NOT VALID and composite-row CHECKs do not supply this invariant. Other same-statement rewrites/risks remain in aggregation. |
| `OP_NEW_RELATION_OPERATION` | SAFE | A supported operation is confined to established new-window storage, including relevant affected relations/retained-lock checks. | A known new target alone cannot discharge opaque effects, an old referenced relation, or a scan under an old-table lock. |
| `OP_METADATA_ONLY` | SAFE | Catalog/session-corroborated supported metadata change, literal lock-timeout setting, already-validated constraint, or positive no-build/no-validation no-op. | Guarded existing-column/absent-table no-ops require catalog corroboration. An existing-target ALTER still acquires its lock; callbacks remain unproved. No catalog change alone is insufficient for arbitrary SQL. Independent lock/scan/rewrite risk remains. |
| `OP_STATEMENT_UNSUPPORTED` | UNKNOWN | Missing supported meaning, physical/old-new identity, catalog corroboration, prior constraint facts, no-scan proof, or complete effects. | Default unknown helper also covers after-only compound-lock timing and an otherwise unproved action. Supply exact supported evidence; no observed rewrite does not prove no scan/index work. |
| `OP_DATABASE_CALLBACK_UNPROVEN` | UNKNOWN | Enabled applicable event/procedural callbacks can perform unmodeled work for this command. | Command-tag restrictions and actual rewrite events scope activation. Compatibility gets a separate `MIGRATION_DATABASE_CALLBACK_UNPROVEN` when these callbacks may affect data. Inspect callbacks; do not infer purity from unchanged catalogs. |

Observed blocking modes are ShareLock, ShareRowExclusiveLock, ExclusiveLock and AccessExclusiveLock on physical tables, partitioned tables or materialized views. Index-only locks are not relabeled as table locks. The supported command proofs establish AccessExclusiveLock for catalog-confirmed ALTER metadata/NOT NULL/CHECK/type changes, ShareRowExclusiveLock for FK owners and referenced tables (including inline FKs on new tables), and ShareLock for ordinary index builds. Missing targets under IF EXISTS do not invent a lock identity. Required modes are reported separately from sampled locks, including after autocommit.

A positive `MIGRATION_LOCAL` or `MIGRATION_SESSION` timeout must be present before the supported command and unchanged afterward, with complete effects and no opaque callbacks. A verifier-injected, unknown-origin, zero or after-only value does not establish authored protection. `lock_timeout` bounds acquisition waiting, never lock holding; retained-lock scan and rewrite risks remain. Table-size metadata grades RISKY severity only, using original baseline names through rename/drop; missing estimates stay conservative and fixture sizes are not production evidence.

A completed empty measured window aggregates operational SAFE without inventing a statement/rule; an absent legacy assessment is unavailable, and an incomplete window cannot certify SAFE. `--fail-on-operational` is policy: after compatibility passes, operational non-SAFE/unavailable returns 4; runtime/incomplete remains 3. Selecting `--fail-on breaking` permits UNKNOWN compatibility but still returns 4 when the requested operational gate does not pass.

## Runtime failures and checkpoint states: no compatibility rule

Sources: `postgres/VerificationRuntime.kt`, `CommittedMigrationCoordinator.kt`, `DeferredQueryPlanning.kt`, `CanonicalCatalog.kt`, `PostgresVerifier.kt`, `PostgresOperationalMonitor.kt`, `PostgresQueryPlanner.kt`, and CLI `VerificationCheckpoint.kt`/`Main.kt`. `VerificationException.stage` identifies failure to complete verification. An execution failure is exit 3, not UNKNOWN or BREAKING. Checkpoints preserve only completed evidence; replay of an incomplete checkpoint exits 3. Process-level termination can have a signal exit status; its preserved checkpoint still remains incomplete rather than a compatibility verdict.

| Exact stage | Evidence / recovery |
| --- | --- |
| `DATABASE_START` | Owned PostgreSQL/Testcontainers startup failed. Preserve the cause chain; check Docker, required PostgreSQL/Ryuk images and CI cleanup configuration. No compatibility run completed. |
| `BASELINE_EXECUTION_FAILED` | Flyway could not build the supplied baseline (unless a timeout supplies the more specific stage). Repair the actual baseline SQL/runtime inputs. This differs from SQL mappings already invalid on a successfully built baseline. |
| `BASELINE_VALIDATION_FAILED` | Flyway validation rejects the constructed/restored baseline, e.g. checksums/history. Repair baseline/cache inputs instead of accepting it as compatibility debt. |
| `MIGRATION_EXECUTION_FAILED` | Pending Flyway execution/callback failed, including unavailable container/connection or malformed migration SQL. Retain the current migration filename/version and cause; no completed target schema is certified. |
| `MIGRATION_TIMEOUT` | The original pending-migration budget covers SQL, history/COMMIT, catalog checks, committed query workers and publication; expiry aborts registered connections. An execution SQLSTATE 57014 may also explicitly report timeout. Increase a deliberately sized bound or fix the blocked/slow operation. This is not a structural UNKNOWN. |
| `COMMITTED_SCHEMA_CHANGED` | The durable catalog differs from the precommit capture under canonical inspection, so previously captured evidence cannot certify that committed state. Earlier checkpoints survive. Review commit-time effects; no stale plans or failed step are published as completed. |
| `PENDING_PLANNING_SESSION_CHANGED` | A committed verification connection or worker changes its expected session while checks are running. Its evidence is incomplete; the stage retains the original migration and exits 3. A fresh session already differing from the baseline policy is instead unverified query evidence (`EPOCH_SESSION_UNPROVEN`), not this infrastructure stage. |
| `GLOBAL_TIMEOUT` | Whole verification exceeds its deadline, including startup; work is cancelled and owned-container cleanup is started without delaying timeout delivery. Preserve/replay only completed checkpoints. |
| `INTERRUPTED` | Verification thread is interrupted, or CLI shutdown records interruption. Cancellation is not per-query extraction debt; partial reports stay incomplete. |
| `PROGRESS_REPORT_FAILED` | A progress callback cannot durably publish its checkpoint. Repair output/filesystem/callback handling; execution evidence cannot be represented as a completed verdict. |
| `OPERATIONAL_MEASUREMENT_FAILED` | Flyway statement observation fails or its identity/session facts cannot be measured. The migration may have run, but measured verification did not complete; preserve migration and cause. |

A pending migration becomes a completed report step only after a successful commit and all selected checks. Typed verification failures wrapped by Flyway retain their specific stage and migration; a later callback does not reattribute an earlier deferred failure. Generic signal checkpoints do not yet carry a separate pending-worker-stage identity.

Checkpoint-only labels: `IN_PROGRESS` is written before/during the run; `INCOMPLETE` marks closure without a successful finalized report; `RUNTIME_FAILURE` is the fallback when an unexpected failure has no more specific VerificationException stage. Invalid CLI/JSON/descriptor input, linkage errors and other unexpected top-level Throwables also return 3; not every failure occurs late enough to have a checkpoint file. Fatal VM failures and cancellation are not converted to recoverable extraction UNKNOWNs.

Planner infrastructure classification explicitly propagates connection exceptions and SQLSTATE classes 08, 25, 40, 53, 57, 58, XX, plus 55P03 and missing SQLSTATE. A non-infrastructure baseline SQL error can be `BASELINE_SQL_UNVERIFIED`; a migration SQL execution error is still an execution failure. Database behavior callbacks, unsupported SQL semantics and optional row-witness rejections are different cases—do not conflate them with infrastructure.

## Metadata and API limits

Missing decoder/input facts and graph inventory retain conservative defaults: `readDomainComplete=false`, `stringInputLengthUnrestricted=false`, and absent selected result positions or operation-local catalog graphs do not establish positive proofs. Grouped source IDs and `catalogChanged` describe evidence and reporting; they do not promote UNKNOWN to SAFE.

Data-direction rules retain their own selected-decoder, direct-producer and whole-row-admission guards. A structural graph or compatible widening proof does not automatically discharge a separate `DATA_*` uncertainty. Baseline acceptance uses fingerprints and gate aggregation rather than deleting evidence. Custom findings supplied directly to the core API are outside this built-in rule inventory.
